# ADR 0015 — Closed-alpha access is a separate, database-enforced gate

## Status

Accepted and deployed to development for Phase 6B.

## Decision

Closed-alpha admission is separate from the account lifecycle. `users.status`
continues to describe whether an account may operate at all, while
`alpha_access_status` records `pending`, `active`, or `suspended` admission.
Existing development users are grandfathered as active. A newly observed Telegram
identity is created pending and lifecycle-blocked until an invitation is redeemed.

Invitation codes are generated by a guarded operator script. Only the SHA-256 of
the normalized code is sent to or retained by Postgres. Redemption locks the user
and invite rows, checks expiry and capacity, records one immutable redemption, and
activates both gates in one transaction.

Commands and callbacks check admission for immediate UX. The database remains the
enforcement point: pending and suspended users have a non-active lifecycle status,
so ingestion and quota RPCs refuse work before a job, quota charge, or provider
call can be created. Old inline buttons therefore cannot bypass a later suspension.

Phase 6B also adds configurable UTC-day limits alongside the existing monthly
plan limits. Reservations serialize on the existing monthly bucket lock, then
lock the daily bucket, so concurrent requests cannot overspend either allowance.

These are database configuration, not application constants. The approved monthly
limits remain unchanged.

## Consequences

- An invitation can be revoked or expire without exposing its raw code.
- Suspending a user blocks new messages, commands, callbacks, and provider quota.
- `/usage` shows both UTC-day and UTC-month counters.
- Operator access changes remain server-side and are not Telegram commands.
- Phase 6C can evolve deletion/privacy lifecycle without overloading the alpha
  admission vocabulary.
